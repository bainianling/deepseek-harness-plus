# Agent Note: 推理控制标签不进入聊天展示

Status: implemented

[English](2026-08-30-reasoning-control-tags-stay-out-of-chat.md) | 中文

## Problem

部分推理提供方偶尔会在其流式推理文本中包含 `<thinking>`、`<analysis>` 等 XML 风格控制分隔符。Harness 已经用独立块类型承载推理，因此展示这些分隔符只会暴露面向传输的标记，不会增加信息。分隔符还可能跨 chunk 到达，使未完成标签短暂出现在运行中摘要里。

如果编码 agent persona 要求在用户可见回复中输出 thinking 或 reasoning，也会提高这种情况的发生率。这混淆了提供方推理通道与 commentary、最终回答文本。

## Decision

`ReasoningRow` 从持久化推理块派生展示文本。它以不区分大小写的方式移除完整的 `think`、`thinking` 和 `analysis` 分隔符，并在流式组装过程中暂不展示位于尾部的上述分隔符前缀。会话事件和存储的推理文本保持不变，供重放与诊断使用。

标准编码 persona 要求模型把私有推理保留在提供方推理通道中，并禁止在用户可见的 commentary 与最终回答里输出内部控制标记。它还要求模型复用已确定事实、批量执行相互独立的检查、避免重复搜索或重复计划，并在证据充分后进入聚焦的实现与验证。

## Alternatives considered

**重写适配器流事件。** 被拒绝，因为适配器会改变持久化的提供方输出和所有下游消费方，而该缺陷只属于展示层；原始推理对诊断仍有价值。

**过滤普通 assistant 文本。** 被拒绝，因为用户可能合理地要求 XML 示例，或在最终回答中讨论 `<thinking>` 语法。推理行已经标识出这些 token 属于传输分隔符的唯一内容类别。

**只依赖 persona。** 被拒绝，因为历史会话和提供方生成的分隔符仍会显示，而且上游模型未必始终遵守提示词。

## Consequences

流式摘要和展开后的推理正文都会省略这些已知分隔符，包括尾部未完成的分隔符前缀。其他尖括号文本继续显示。原始日志保持无损，普通 assistant Markdown 不受影响。使用标准 persona 的新会话会收到效率与通道分离指导；正在运行的 preset 代际会保留其已组装提示词，直到 host 或代际被替换。
